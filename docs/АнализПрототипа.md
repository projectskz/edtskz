# Анализ прототипа: конструктор БП в «1С:Управление по целям и KPI 3.1»

| | |
|---|---|
| Источник | `Configuration.xml` выгрузки базы клиента ОТЭКО (`D:\oteko bp`) |
| Конфигурация | «1С:Управление по целям и KPI, ред. 3.1», версия 3.1.1.1, фирма «Волгасофт-проект» |
| Режимы | Совместимость 8.3.20, совместимость расширений 8.5.1, интерфейс «Такси» |
| Глубина анализа | ⚠ **Только по составу и именам объектов.** Кода, реквизитов и форм в `Configuration.xml` нет, поэтому выводы ниже — гипотезы. Как их проверить, см. п. 5. |

Цель анализа — позаимствовать удачные **идеи архитектуры**, а не повторять реализацию. Прототип — модуль внутри конкретного продукта (KPI), наш продукт — универсальное расширение.

## 1. Состав подсистемы бизнес-процессов (по именам)

| Назначение | Объекты прототипа | Предполагаемая роль |
|---|---|---|
| Виды процессов (шаблоны) | `Справочник.KPI_ВидыБП`, `РС.KPI_ОбъектыВидовБП`, `РС.KPI_ПараметрыВидовБП` | Шаблон процесса, привязка к типам объектов, параметры шаблона |
| **Элементы схемы** | `Справочник.KPI_ЭлементыБП`, `Перечисление.KPI_ТипыЭлементовБП` | Шаги схемы — **элементы справочника**, а не строки табличной части |
| Переходы | `РС.KPI_ИсходящиеТочкиБП` | Исходящие точки элемента: ветки, выходы, вероятно кнопки результата |
| Параллельность | `РС.KPI_РазделениеМаршрутаБП` | Разделение маршрута на параллельные ветки |
| Адресация | `РС.KPI_ИсполнителиБП`, `РС.KPI_РолиБП`, `Справочник.KPI_СтруктураКомпании` (+ ~10 объектов структуры), `Перечисление.KPI_ВидОтветственных` | Исполнители шага; роли, привязанные к собственной структуре компании |
| Переменные | `ПВХ.KPI_Переменные`, `РС.KPI_ПараметрыБП`, `РС.KPI_ПараметрыБППостоянные` | **Типизированные переменные через план видов характеристик**; значения по экземпляру и постоянные |
| Исполнение | `БизнесПроцесс.KPI_БизнесПроцесс`, `Задача.KPI_Задача`, `РС.KPI_ЗадачиОбъектовБП`, `РС.KPI_ПредставлениеЗадачиБП` | **Один универсальный платформенный БП** как «носитель», маршрут берётся из справочников. Связь задач с объектами, денормализованное представление задачи |
| Копии и исключения | `РС.KPI_ДублироватьЗадачуБП`, `РС.KPI_ИсключенияБизнесПроцессов` | Дублирование задачи (копия / информирование); исключения из автозапуска |
| История | `РС.KPI_ХроникаБизнесПроцессов` | Хроника (журнал) процесса |
| Замещение | `Документ.KPI_ПриказОЗамещении`, `РС.KPI_Замещение`, `РегЗадание.KPI_КонтрольЗамещения`, `ФО.KPI_ИспользоватьЗамещениеСтруктур` | **Замещение оформляется документом-приказом**, регистр — его движения, регламентное задание включает и выключает замещения |
| Передача и делегирование | `Конст.KPI_ФункционалПередачиЗадачи`, `Конст.KPI_РазрешитьПереносДелегированныхЗадач` | Передача задачи другому и перенос делегированных задач |
| «Взять в работу» | `Конст.KPI_БП_ЗавершатьДругиеЗадачиЭтапаПриПринятииВИсполнение` | Когда один из исполнителей принял задачу этапа, остальные задачи этапа снимаются |
| Пустые роли | `Конст.KPI_БП_РазрешитьАдресациюПустымСтруктурам` | Настройка поведения при пустой роли |
| Оповещения | `РС.KPI_НастройкаОповещенийВБП`, `РС.KPI_Оповещения_СтекОповещений`, `Справочник.KPI_Оповещения_ШаблоныПодстановки`, `Справочник.KPI_СобытияОповещения`, `Справочник.KPI_Оповещения_ГрафикиОповещений`, `РС.KPI_ЛокальныеОповещения`, `Перечисление.KPI_СпособыОповещения` | Настройки по событиям, **очередь («стек»)**, шаблоны с подстановками, графики отправки, локальные (в интерфейсе) оповещения |
| **Группировка писем** | `Документ.KPI_ГруппировкаОповещенийБП`, `РС.KPI_ОповещенияБПКГруппировке`, `Перечисление.KPI_СпособыГруппировкиПисемБП`, `Конст.KPI_ШаблонСгруппированногоПисьмаОпоевщенийБП`, `Конст.KPI_ПериодОповещенияОЗадачахПользователя` | Оповещения копятся и уходят **одним сгруппированным письмом за период** |
| Кнопки | `ОбщийМакет.KPI_КнопкиБП` | Вероятно, набор картинок или описаний кнопок для динамических команд |
| Запуск | `ОбщаяКоманда.KPI_БП_ЗапускБизнесПроцессов`, `РегЗадание.KPI_ЗапускБП` | Ручной запуск и запуск по расписанию |
| Контроль сроков | `РегЗадание.KPI_АвтоЗавершениеПросроченныхЗадач` | Автозавершение просроченных задач |
| Администрирование | `Обработка.KPI_АдминистрированиеБП`, `ОбщаяКоманда.KPI_АдминистраторБП`, `Отчет.KPI_ОтчетПоКонструкторуБП` | Панель администратора и отчёт по конструктору |
| Права | `Роль.KPI_ПользовательБизнесПроцессов`, `Роль.KPI_РедактированиеБизнесПроцессов` | Две роли: участник и методолог |
| Модули | `KPI_УправлениеБизнесПроцессамиКлиент / Сервер / СерверВызовСервера`, `KPI_УправлениеБизнесПроцессамиСерверПросвещение` | Ядро и модуль под отдельного клиента |
| Доработки клиента | `Справочник.ОТЭКО_Процессы`, `РС.ОТЭКО_Процессы` | Процессы ОТЭКО, связь с конструктором требует проверки |

**Эволюция.** Объекты `Удалить_KPI_БП_Планирование`, `Удалить_KPI_БП_SMARTЗадачи`, `Удалить_KPI_ЗадачиБП`, `Удалить_KPI_БП_НастройкаБизнесПроцессов` показывают, что продукт ушёл от **жёстко запрограммированных процессов** к конструктору. При этом `БизнесПроцесс.KPI_БП_ПодведениеИтогов` остался жёстким. Это подтверждает наш выбор: конструктор с первого дня, без «зашитых» процессов.

## 2. Что берём (идеи, реализация своя)

| № | Идея прототипа | Как применяем у нас | Изменение в архитектуре |
|---|---|---|---|
| И-1 | Шаги схемы — **элементы справочника**, переходы — **регистр** | Совпадает с вашим решением «все настройки — в справочниках и регистрах». Шаги, переходы, кнопки и оповещения выносим из табличных частей версии в отдельные объекты, подчинённые версии схемы. | П. 4.1: `кбп_ЭлементыСхем` (справочник, владелец — `кбп_ВерсииСхем`), `кбп_ПереходыСхем`, `кбп_КнопкиШагов`, `кбп_ОповещенияШагов` (регистры сведений). При публикации версия копируется целиком. |
| И-2 | Переменные через **ПВХ** | Типизированные переменные с выбором типа в пользовательском режиме и нормальными отборами в запросах. | П. 4.1: `ПВХ.кбп_ПеременныеПроцессов` (владелец — схема). ТЧ `Переменные` процесса: `Переменная` (ссылка ПВХ) + `Значение` (Характеристика). |
| И-3 | **Замещение документом** | Оформление замещения документом: кто, кого, когда, основание, согласование. Движения — в регистр. Есть аудит и можно провести или отменить. | П. 4.2: `Документ.кбп_Замещение` → регистр `кбп_Замещения` подчинён регистратору. |
| И-4 | **«Взять в работу»** снимает задачи у остальных | Режим шага «любому из» явно получает механику принятия: кто принял, тот исполняет, у остальных задача снимается. | П. 6.2: состояние задачи «ВРаботе», операция `ПринятьКИсполнению`. ТЗ: ФТ-411. |
| И-5 | **Группировка оповещений** в одно письмо за период | Дайджест вместо десятков писем. Для каждого пользователя и канала: сразу / раз в N минут / раз в день. | П. 9: статус «Ожидает группировки» в очереди; задание `кбп_РассылкиПоРасписанию` собирает дайджест. ТЗ: ФТ-608. |
| И-6 | **Дублирование задачи** (копия) | Информационные копии задачи наблюдателям без права выполнения («для сведения»). | ТЗ: ФТ-412, шаг «Копии». |
| И-7 | **Исключения** из автозапуска | Список исключений в правилах запуска (объекты, организации, пользователи). | ТЗ: ФТ-108 дополняется. |
| И-8 | Автозавершение просроченных задач | Действие шага при просрочке: эскалация / автовыполнение с результатом по умолчанию / ничего. | ТЗ: ФТ-308 дополняется. |
| И-9 | Постоянные параметры | Константы схемы (например, лимит суммы), которые меняются без новой версии схемы. | П. 4.1: регистр `кбп_ПараметрыСхем`. |
| И-10 | Локальные оповещения | Оповещения внутри 1С: счётчик и всплывающие уведомления, без почты. | Канал «Интерфейс» в п. 9. |

## 3. Что не берём и почему

| Решение прототипа | Почему не подходит | Наше решение |
|---|---|---|
| **Платформенный `БизнесПроцесс` как носитель** универсального маршрута | В расширениях платформенные бизнес-процессы и задачи ограничены (проверить на 8.3.27 в прототипе). Любая доработка маршрута-«носителя» требует конфигуратора. Появляется двойная модель состояния. | Собственный движок на маркерах (АР-2, АР-5). |
| **Собственная структура компании** (`KPI_СтруктураКомпании`, ~15 объектов) | В ERP, КА, УХ, УНФ, БП уже есть организации, подразделения, структура предприятия. Дублирование — лишняя работа для внедрения. | Объекты адресации из базовой конфигурации через адаптер (п. 3.2, 7). |
| `ОпределяемыйТип.KPI_ОбъектыБП` для предметов процессов | Состав определяемого типа — это правка метаданных под каждую конфигурацию. | `ЛюбаяСсылка` + список типов из `Метаданные` (ФТ-104). |
| Отдельные регистры под конкретные этапы (`KPI_ОтветственныеПервыйЭтапНачисленияЗП`, `…ВторойЭтапСогласованиеПремии` и т. п.) | Логика конкретного процесса зашита в метаданные. | Универсальные роли + объекты адресации (п. 4.2). |
| ~30 **констант** настроек БП | Рост числа объектов метаданных, плохо переносится между базами. | Регистр настроек `кбп_Настройки` (ключ → значение) + настройки уровня схемы и шага. |
| Модули под конкретных клиентов в ядре (`…СерверПросвещение`, `KPI_Русклимат`) | Код клиента смешан с кодом продукта. Обновление продукта ломает доработки клиента. | Точки расширения в `кбп_ПроцессыПереопределяемый` + доработки клиента в **его** расширении. |
| Жёсткий `KPI_БП_ПодведениеИтогов` рядом с конструктором | Два механизма процессов в одном продукте. | Только конструктор. Типовые процессы поставляются как **эталонные схемы JSON** (`examples/`). |

## 4. Предлагаемые изменения в документах

Если согласны, внесу их в ТЗ и архитектуру:

1. **Модель схемы (И-1)**: шаги — справочник `кбп_ЭлементыСхем`, переходы, кнопки и оповещения — регистры сведений, всё в разрезе версии схемы. Табличные части у `кбп_ВерсииСхем` убираются.
2. **Переменные через ПВХ (И-2)**: `ПВХ.кбп_ПеременныеПроцессов`.
3. **Замещение документом (И-3)**: `Документ.кбп_Замещение`, регистр `кбп_Замещения` — подчинённый регистратору.
4. **Новые требования ТЗ**: ФТ-411 «Взять в работу», ФТ-412 «Копии для сведения», ФТ-608 «Группировка оповещений», дополнения ФТ-108 (исключения) и ФТ-308 (автозавершение просроченных).
5. **Настройки** — регистр `кбп_Настройки` вместо констант, `кбп_ПараметрыСхем` для постоянных параметров схемы.
6. **Канал «Интерфейс»** для локальных оповещений.

## 5. Что нужно для более глубокого анализа

Этот анализ сделан по одному файлу `Configuration.xml`. Чтобы проверить гипотезы (особенно как устроены конструктор на форме, переходы и связь с платформенным БП), нужны **папки этих объектов** из той же выгрузки. Их можно заархивировать в zip и прислать сюда же:

```
Catalogs\KPI_ВидыБП\          Catalogs\KPI_ЭлементыБП\        Catalogs\ОТЭКО_Процессы\
Enums\KPI_ТипыЭлементовБП\    ChartsOfCharacteristicTypes\KPI_Переменные\
InformationRegisters\KPI_ИсходящиеТочкиБП\   InformationRegisters\KPI_РазделениеМаршрутаБП\
InformationRegisters\KPI_ИсполнителиБП\      InformationRegisters\KPI_РолиБП\
InformationRegisters\KPI_ПараметрыБП\        InformationRegisters\KPI_ХроникаБизнесПроцессов\
InformationRegisters\KPI_Замещение\          InformationRegisters\KPI_НастройкаОповещенийВБП\
BusinessProcesses\KPI_БизнесПроцесс\         Tasks\KPI_Задача\
Documents\KPI_ПриказОЗамещении\              Documents\KPI_ГруппировкаОповещенийБП\
CommonModules\KPI_УправлениеБизнесПроцессамиКлиент\
CommonModules\KPI_УправлениеБизнесПроцессамиСервер\
CommonModules\KPI_УправлениеБизнесПроцессамиСерверВызовСервера\
CommonTemplates\KPI_КнопкиБП\                DataProcessors\KPI_АдминистрированиеБП\
```

(плюс одноимённые `.xml` рядом с каждой папкой). Главное — форма элемента `KPI_ВидыБП` (или `KPI_ЭлементыБП`) с графической схемой и модуль `KPI_УправлениеБизнесПроцессамиСервер`.
